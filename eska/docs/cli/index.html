ESKA · справочник CLI

Все команды ESKA

Синтаксис команд приведён для ESKA 0.38.0. Выберите программу и команду в таблице её раздела. В раскрывающемся блоке перечислены аргументы и параметры. Для просмотра справки достаточно установленного бинарника.

Команда eska --version показывает версию программы, а eska version читает версию проекта 1С. Параметр --project-dir задаёт начальный каталог для поиска проекта. У команд clone, new и init он задаёт базовый каталог для относительных путей. В примерах замените имена проектов, файлов и объектов на свои.

Практическое руководство · Назначение компонентов

Руководство Практический пример Установка
01

eska

Из каталога с выгрузкой Designer XML выполните eska init, чтобы создать манифест. Для нового проекта используйте eska new. Команда eska doctor покажет, какие зависимости доступны для дальнейшей работы.

Для изменения метаданных начните со схемы выбранного проекта. В этом примере команда проверяет возможность создать документ и сохраняет план. Последняя строка применяет его к исходникам.

eska metadata object-schema --kind document --format json
eska metadata create --kind document --name Заказ --dry-run --no-input --format json > plan.json
eska metadata create --plan plan.json --no-input --format json

Для workspace укажите проект через -p ИМЯ. Если после предпросмотра изменились исходники, получите новый план. Примеры добавления реквизитов и модулей, операций формы и восстановления записи есть в руководстве по созданию метаданных.

eska metadata create: синтаксис и все параметры 
Создать объект метаданных, при необходимости на основе существующего.

Usage: eska metadata create [OPTIONS]

Options:
      --kind <KIND>                 Ключ типа из object-schema, например catalog, document или common-module.
      --lang <ЛОКАЛЬ>               Выбрать язык интерфейса
      --name <NAME>                 Имя нового элемента в конфигурации
      --project-dir <КАТАЛОГ>       Искать проект из указанного каталога; для clone/new/init — базовый каталог (по умолчанию — текущий)
      --parent <PARENT>             Идентификатор родителя; по умолчанию — корень проекта, для копии — исходный родитель.
      --template <TEMPLATE>         Идентификатор существующего объекта того же типа, используемого как образец.
      --set <PROPERTY=VALUE>        Явное значение скалярного свойства; можно повторять. Идентификаторы менять нельзя.
      --reference <PROPERTY=VALUE>  Ссылка в свойстве-списке; повторяйте для нескольких значений, например RegisterRecords=AccumulationRegister.Остатки.
      --type <PROPERTY=TYPE>        Тип в свойстве-списке; повторяйте для составного типа, например Source=cfg:DocumentObject.Заказ или Type=xs:string.
      --input <INPUT>               Файл запроса создания в JSON с версией схемы, либо - для stdin
      --plan <PLAN>                 Сохранённый JSON-вывод add --dry-run, либо - для stdin; сохраняет рассмотренные идентификаторы
      --dry-run                     Вернуть подготовленный план создания без записи исходников
      --no-input                    Отключить все вопросы; при нехватке параметров вернуть ошибку
  -h, --help                        Показать справку
  -p, --project <PROJECT>           Выбрать один проект рабочего пространства
      --format <FORMAT>             Формат вывода; add использует human, прежние операции и create-schema — JSON [possible values: human, json]

Файлы настроек проекта

eska-project --project-dir ПУТЬ settings-project show --file manifest --format json
eska-project --project-dir ПУТЬ settings-project preview --file ignore --format json
eska-project --project-dir ПУТЬ settings-project save --file attributes --format json

--project-dir указывает на каталог с eska.toml. Для отдельного участника workspace укажите его каталог. Значения manifest, ignore и attributes выбирают соответственно eska.toml, .gitignore и .gitattributes. Поддерживаются файлы UTF-8 до 512 КиБ.

В JSON версии 1 успешный ответ содержит kind: "project-settings", status: "ready", revision и value. Для манифеста value содержит объект со значениями TOML. Команда show для манифеста также возвращает format_schema и format_presets для встроенных профилей. При чтении манифеста участника format_inherited содержит таблицу [format] из корневого манифеста workspace, если она задана. Для файлов Git value содержит текущий текст, а git_template содержит встроенный шаблон ESKA. Отсутствующий файл Git возвращает пустую строку и revision: null.

preview и save читают JSON из stdin. Укажите ревизию из show. Для манифеста передайте список edits, где path содержит имена полей и нулевые индексы массивов. Запись без value удаляет элемент.

{
  "revision": "РЕВИЗИЯ",
  "edits": [{"path": ["format", "common", "column_limit"], "value": 120}]
}

Для файла Git передайте полное новое содержимое в value.

{"revision": null, "value": "*.xml text eol=lf\n"}

preview возвращает исходную ревизию, предложенные значения, тексты before и after и признак changed. save возвращает сохранённую ревизию. При конфликте ревизий ответ содержит status: "error" и error.code: "settings_changed". Прочитайте файл заново перед повтором.

Правки раздела [tools.bsl-analyzer] проходят проверку check-config. Для выбора исполняемого файла используется --analyzer ФАЙЛ, переменная ESKA_BSL_ANALYZER или команда bsl-analyzer-app на PATH. Если передан --analyzer, после записи изменённого манифеста ESKA пытается обновить производный bsl-analyzer.toml. Поле analyzer сообщает отдельный итог обновления. --application ИМЯ выбирает приложение workspace для проверки или обновления.

Локальные профили запуска

Для команд show, save и validate справка доступна через eska-project settings-local --help.

eska-project --project-dir <путь> settings-local show --format json
eska-project --project-dir <путь> settings-local validate
eska-project --project-dir <путь> settings-local save --format json

show возвращает settings, revision и git_protection в JSON версии 1. Документ содержит локальные пути и адреса. validate проверяет объявления профилей. save читает JSON с полями revision и settings из stdin и возвращает новую ревизию. Для первого сохранения используйте revision: null. Если файл изменился после чтения, прочитайте его заново и повторите правки.

Файл .eska/settings_local.toml относится к одному проекту. Если проект находится в Git, сохранение допускается, когда файл исключён и его нет в индексе. Для ранее созданного проекта проверьте .gitignore или локальные исключения репозитория. show сообщает о проблеме защиты в git_protection.

Каждый профиль состоит из отдельных таблиц для базы, платформы и HTTP-отладки. Следующий пример содержит только условные значения.

[test.infobase]
kind = "file"
path = "local/test-base"

[test.runner]
kind = "distrobox"
container = "onec"
version = "8.3.27.2342"

[prod.infobase]
kind = "cluster"
host = "server.example.invalid"
name = "demo"

[prod.runner]
kind = "local"

[prod.debug]
url = "http://debug.example.invalid:1550"
auto_attach_types = ["ManagedClient", "Server"]

[prod.authentication]
user = "developer"
password_env = "ESKA_DEMO_PASSWORD"

Путь к файловой базе может быть относительным к корню проекта. Профиль автономной базы использует kind = "standalone", url и name. Для применения изменений задайте admin_pid, локальный PID процесса ibsrv в выбранном раннере. Внутри Git-репозитория для проверки индекса и правил исключения используется установленный eska-vcs. В runner можно указать точную version и абсолютный путь ibcmd. debug.url задаёт отдельный HTTP-сервер 1С. Для файловой базы вместо debug.url можно задать debug.managed = true и необязательный debug.port. Управляемый сервер слушает 127.0.0.1; если порт не указан, его выбирает dbgs. Без debug.auto_attach_types автоматически подключаются ManagedClient, Client, Server и ServerEmulation. Пустой список оставляет только ручной выбор. Поддерживаемые типы — Client, ManagedClient, WEBClient, COMConnector, Server, ServerEmulation, WEBService, HTTPService, OData, JOB, JobFileMode, MobileClient, MobileServer, MobileJobFileMode, MobileManagedClient, MobileManagedServer. В проекте типа processing таблица debug.external_processing задаёт artifact и необязательный debug_url для подключения к загруженной копии. Относительный путь артефакта считается от корня проекта. Отладка EPF из проекта password_env содержит имя переменной окружения, а её значение передаётся отдельно от TOML.

Запуск и применение изменений

eska run [--profile test] [--format human|json] запускает тонкий клиент из установки 1С, выбранной в профиле проекта. Команда ждёт завершения клиента. eska-build run принимает те же параметры.

eska apply [--profile test] [--application <имя>] [--initialize] [--confirm <токен>] [--format human|json] показывает выбранную базу, версию платформы и список файлов. Сначала запустите команду без --confirm. Для применения повторите команду с полученным токеном и теми же параметрами. После обновления eska-build заново получите токен предпросмотра. eska-build apply принимает те же параметры. В режиме JSON команда отправляет события apply_progress с фазами import и apply в stderr. Для частичного импорта plan.import_files перечисляет файлы в порядке передачи в ibcmd, включая неизменённые сопутствующие файлы. В остальных режимах import_files равно null. Поле plan.changes содержит изменения исходников. При структурном частичном импорте plan.object_changes группирует пути по объектам. В группе указаны kind (language, common_form, role, common_module или common_picture), operation (added, renamed или removed), name, previous_name и paths. Для переименования paths включает прежние и новые пути. Если при переименовании или удалении общей картинки в XML выбранного компонента остаются ссылки на прежнее имя, plan.mode равен unsupported, а plan.picture_references перечисляет файлы для проверки. Исправьте ссылки и повторите предпросмотр.

В JSON-плане поле inspection содержит отдельные результаты сравнения сохранённых исходников (sources) и фактического поколения базы (database) с последним успешным применением на момент проверки плана. Оба поля принимают значения unknown, unchanged или changed. baseline_generation и database_generation показывают известные токены, pending_apply отмечает незавершённую операцию. status принимает значения up_to_date, local_changes, database_changed, both_changed, unknown_baseline, database_unavailable или incomplete. Изменение поколения говорит об изменении базы. Список файлов описывает только разницу сохранённых исходников с применённым снимком. При отказе в предпросмотре из-за снимка, поколения или незавершённого применения ответ содержит review.inspection и review.changes. При неизвестном снимке review.changes равно null. Коды ошибок и коды выхода сохраняются.

Первый запуск для базы требует отдельного предпросмотра с --initialize, который импортирует всю конфигурацию Designer XML. После успеха в .eska сохраняются контрольные суммы файлов, идентичность дескрипторов и поколение конфигурации. Частичный режим передаёт существующие BSL, правки свойств языка и форм, а также существующие XML-макеты управляемых форм. Для свойств справочника с набором файлов управляемых форм план включает дескриптор справочника, дескрипторы и макеты его форм. Сопутствующие файлы видны перед подтверждением. Для XML сверяются идентичность и структура дескриптора с применённым снимком. Если снимок создан версией без этих сведений, их записывает подтверждённый полный импорт. Смена ветки учитывается по байтам сохранённых файлов. Частичный импорт поддерживает добавление, удаление и переименование языков и общих управляемых форм с XML-макетом и необязательным модулем BSL. В плане сверяются записи ChildObjects, наличие всех файлов объекта и UUID. При удалении в список импорта входит неизменённый дескриптор языка по умолчанию. Для этого сценария нужен применённый снимок со сведениями о корневом дескрипторе. Изменения других частей Configuration.xml, формы с дополнительными файлами и неподдержанные структурные изменения требуют предпросмотра полного импорта.

Для общей картинки основной конфигурации или собственного объекта установленного расширения частичный импорт передаёт Ext/Picture.xml и единственный файл из Ext/Picture/, на который ссылается XML. Поддерживаются имена Picture.svg, Picture.png, Picture.bmp, Picture.gif, Picture.ico, Picture.jpg, Picture.tif, Picture.zip и Picture без расширения. При смене формата план показывает удаление старого файла и добавление нового. Импорт получает обновлённый Ext/Picture.xml и новый файл. Изменение свойств добавляет дескриптор картинки. Добавление и переименование по UUID передают весь набор с Configuration.xml. Удаление передаёт Configuration.xml с неизменённым дескриптором языка или роли по умолчанию.

Для уже заимствованной по имени картинки с тем же UUID частичный план поддерживает замену картинки, смену формата, очистку и возврат к наследованию. Замена передаёт два ресурсных файла. Если Picture остаётся Extended, удаление обоих ресурсов очищает картинку. Удаление состояния Picture возвращает наследование. Эти переходы передают дескриптор картинки. Восстановление переопределения из наследуемого состояния передаёт дескриптор и два ресурсных файла. Для изменения состояния нужен применённый снимок с подтверждённой привязкой. Изменение UUID, привязки и неподдержанные наборы ресурсов требуют предпросмотра полного импорта. Посторонний импорт, частичная ошибка и изменение исходников после предпросмотра блокируют продолжение по прежнему токену. После ошибки проверьте состояние базы перед новым предпросмотром полного импорта.

eska extension install [--profile test] [--confirm <токен>] [--format human|json] показывает план установки отсутствующего расширения InfoBase из Designer XML в тестовую базу основной конфигурации. eska-build extension install принимает те же параметры. Запускайте команду из проекта расширения или укажите его через --project-dir. В Explorer используйте команду «Установить расширение в тестовую базу». План содержит базу, имя, UUID, файлы и поколения установленных зависимостей.

Подтверждение под общей блокировкой apply сверяет снимок файлов, поколение основной конфигурации, зависимости и нативный список расширений. Уже занятое имя или UUID блокирует установку. Внешние операции с базой выполняйте отдельно от подтверждения ESKA. Импорт и применение показываются как отдельные фазы. Снимок apply сохраняется после успешного применения и проверки UUID. Если расширение появилось после прерванной установки, завершите обновление через подтверждённый apply --initialize. В JSON kind равен extension_install, status принимает preview, installed или error.

eska extension remove [--profile test] [--confirm <токен> --force] [--format human|json] предварительно проверяет удаление установленного расширения InfoBase из тестовой базы основной конфигурации. eska-build extension remove принимает те же параметры. Запустите команду из каталога проекта расширения или передайте его через --project-dir. Сначала получите план, затем повторите команду с его токеном и --force. При удалении можно безвозвратно потерять данные расширения. Explorer предоставляет отдельную команду «Удалить расширение из тестовой базы» с выбором проекта, предпросмотром и явным подтверждением.

План содержит целевую базу, версию платформы, имя и UUID расширения и поколения основной конфигурации и расширения. Перед удалением CLI сверяет список установленных расширений и точное содержимое текущей выгрузки под той же блокировкой цели, что и apply. Установленная зависимая часть выбранного workspace-приложения останавливает удаление. Блокировка координирует операции ESKA. Внешние операции с базой следует выполнять отдельно от подтверждения ESKA.

При успешном удалении CLI подтверждает отсутствие расширения и очищает его локальный снимок apply. Если платформа удалила расширение, а сохранение результата прервалось, следующий предпросмотр предложит только очистку оставшегося локального состояния. В JSON kind равен extension_remove, status принимает preview, removed или error. При восстановлении plan.extension_generation равен null, plan.pending_operation равен true.

Чтобы обновить установленное расширение, укажите каталог проекта расширения через eska-build --project-dir <каталог> apply или выберите этот проект в Explorer. Workspace-приложение должно определяться однозначно и содержать проект основной конфигурации и расширение с областью установки InfoBase. Команда использует настройки test основной конфигурации и проверяет имя и UUID установленного расширения и его объявленных зависимостей. Снимок каждого расширения хранится отдельно в .eska основной конфигурации.

Если после ошибки чтения метаданных список платформы подтверждает отсутствие расширения, CLI возвращает extension_not_installed. В JSON error.extension содержит имя отсутствующего расширения, в том числе зависимости. Ошибка получения списка или невозможность прочитать установленное расширение даёт extension_unavailable. Несовпадение UUID имеет код extension_identity_mismatch.

Для первого применения нужен предпросмотр с --initialize. Он импортирует исходники только выбранного установленного расширения. После создания снимка частично применяются изменения существующих BSL и свойств существующей роли, если у роли нет отдельных файлов. Для XML сверяются UUID и структура дескриптора. Если снимок ещё не содержит этих сведений либо XML-изменение выходит за границы поддержанного сценария, нужен предпросмотр полного импорта. Команда обновляет по одному установленному расширению за раз. Для расширений в JSON-плане появляется plan.extension с полями name и uuid. plan.inspection.configuration_generation содержит поколение основной конфигурации, а dependency_generations при наличии зависимостей содержит их поколения по именам из Designer XML. Изменение любого из этих поколений после предпросмотра требует нового подтверждения.

Чтобы применить всё приложение из workspace, передайте --application <имя>. Имя берётся из workspace.members. Сначала применяется основная конфигурация, затем установленные расширения InfoBase в порядке объявленных зависимостей. План показывает состояние и файлы каждого компонента. Операции с внешними обработками и отчётами, установка и удаление расширений в этот план не входят.

Подтверждение связывает планы всех компонентов. ESKA перепроверяет их и последовательно применяет под общей блокировкой базы. При сбое применённые компоненты сохраняют свои снимки. Для продолжения запросите новый план. С --initialize полный импорт предлагается только там, где частичный импорт невозможен или предыдущая операция оставила неподтверждённое состояние. Компоненты без изменений пропускаются.

JSON-ответ для приложения имеет kind: "application_apply". В предпросмотре plan.components содержит планы или причины блокировки каждого компонента, а plan.confirmation содержит общий токен либо null. В событиях apply_progress поле component обозначает имя участника. После выполнения outcomes перечисляет компоненты со статусами applied, unchanged, not_started или failed. При сбое error.component указывает компонент, на котором возникла ошибка, если он уже известен.

Для автономной тестовой базы в admin_pid задаётся PID уже запущенного ibsrv, видимый в выбранном раннере. После перезапуска обновите PID. Профиль prod заблокирован для обеих команд, а кластерный профиль поддерживает только обычный запуск тестового клиента.

eska-build probe --profile test|prod [--format human|json] проверяет наличие тонкого клиента, файла базы либо TCP-доступность настроенных адресов. Проверка доступности не открывает сеанс 1С и не использует пароль.

С --stdin команда читает один профиль в JSON из стандартного ввода (до 128 КиБ). Объект содержит infobase, runner и необязательные debug и authentication в том же формате, что профиль в eska-project settings-local show --format json. --profile задаёт имя профиля. Файл локальных настроек при этом не читается и не записывается. Для недопустимого значения JSON-ответ содержит error.code = "invalid_field" и error.data с именем профиля и поля.

eska-fmt

Из каталога проекта выполните eska-fmt --diff, чтобы увидеть предлагаемые изменения BSL и запросов. Вызов без параметров записывает изменения. Для одного модуля передайте его путь относительно --project-dir.

eska-fmt --dump-config --format json
eska-fmt src/CommonModules/Обмен/Ext/Module.bsl --diff
eska-fmt --check

В режиме --check код 0 означает совпадение с настройками, 1 — нужны правки. Код 2 означает ошибку, 130 — отмену. Выбор правил и настройки BSL, запросов и XML описаны в справочнике форматирования.
